Comparison with prior work. Let n be the number of
records, w the bytes per record, and m the number of 64-

from routing records to hash buckets, and fixed-width AVX-

2.3. Deamortization-friendly Hierarchical ORAM
We now build a hierarchical ORAM whose rebuilds route
records with byte-sliced merge-splits. Moreover, we design it
to make deamortization easier, namely, to let rebuilds run in
the background while requests continue (Section 3).
Read-only hash tables. An access that finds a key in a table
writes the possibly updated record to the online stash, so the
table still holds an older copy of the key. Some schemes mark
this older copy as erased, so that the next rebuild discards
it [10], [23], [26], [27], [30], [39]. Others leave the copy in
place [5], [11], [12], [24], where the newer copy shadows it:
later accesses find the newer copy first and send only dummy
probes to the older copy’s table.
Marking complicates background rebuilding. A rebuild
reads its input tables while accesses continue, so every mark
made during the rebuild would have to be logged and replayed
on the rebuilt table. We therefore leave older copies in place,
so accesses write only to the online stash, and a hash table
never changes after it is built. A rebuild then reads a fixed
snapshot of its inputs, and accesses and rebuilds never write
to the same memory.
Leaving older copies in place also makes writes cheap.
Because the newer copy shadows the older one, a write or
an erasure need not locate the older copy, so MICRORAMA
appends the new record to the online stash without probing the
hash tables, which makes these requests faster than lookups.
For an erasure, the appended record is a tombstone, whose
metadata marks the key absent. Skipping the probes, however,
reveals that a request is a write. An application that must hide
whether a request reads, writes, or erases can therefore issue
every request through one access, which probes the tables,
returns the key’s current value, and then appends the record
that the request asks for. [Tianyao: Report the latency of a
write without probes against a lookup once the library exposes

Shadowing also hides repeated lookups of an absent key.
Such a lookup finds no record to write back. H2O2RAM then
appends an unkeyed dummy record, so a repeated lookup of
the key probes the same buckets again and reveals the repe-
tition [25]. Following earlier work [23], [24], MICRORAMA
instead appends a tombstone, exactly as an erasure does. A
later access for the key then finds the tombstone first, so the
tables already probed for the key receive only dummy probes.
The top level eventually discards tombstones (Appendix A).
Incremental merges. When the online stash fills, its records
may move up several levels at once. H2O2RAM and
MegaBlocks rebuild all of these levels in one step, building a
single table from the stash and the tables of the levels [10],
[22]. We instead view this rebuild as a cascade of merges of
two tables at a time: the stash with the smallest hash table, the
result with the next table, and so on. We call each completed
table that a level passes to the next level a carry. Unlike a
rebuild in one step, a cascade produces a usable table after
every merge. Skipping ahead, Section 3 uses this to run the
merges in the background: accesses continue on the tables
built so far, so they do not stall while a large table is rebuilt.
Every merge of a cascade routes records by the hash of
the cascade’s final table, so the merges together form one
butterfly network over the final table’s buckets (Figure 3).
Comparing to a one-step rebuild, our incremental merges
essentially perform the same work, only in a different order.
The earlier merges have already routed the carry, so a merge’s
preparation routes only its level’s table, the older table, and
the merge’s last stage then combines the two tables.
