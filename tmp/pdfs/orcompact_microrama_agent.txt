MICRORAMA: Microsecond Oblivious Access to Gigabytes of Data
Anonymous Submission
Abstract—Trusted execution environments (TEEs) protect the
contents of memory, but secret-dependent memory accesses can
still leak sensitive information through side channels. Oblivious
RAM (ORAM) complements a TEE by hiding which mem-
ory locations a program accesses. While recent systems such
as H2O2RAM (USENIX’25) and SONIC (USENIX’26) have
substantially improved ORAM throughput inside TEEs, they
remain one to two orders of magnitude slower than non-oblivious
implementations.
We present MICRORAMA, a highly efficient ORAM and
oblivious map (OMAP) for commodity x86 TEEs with AVX-
512. On a 16-core Intel TDX virtual machine and with 227 8-
byte words, our deamortized hierarchical ORAM serves up to
1.04 M requests per second one at a time, 12.8× the throughput
of H2O2RAM and 70% of the throughput of a non-oblivious
std::unordered_map. When requests arrive at half of this rate,
we achieve an average response time of 0.93 µs and a 99th-
percentile response time of 1.4 µs. In comparison, H2O2RAM’s
average and 99th-percentile response times at half of its own
throughput are 4.0 and 90 s, respectively, because its rebuilds
block the requests that arrive in the meantime. When requests
arrive in batches, we serve 3.36 M requests per second on the
same machine, 70× the throughput of SONIC. We use 10.0 GiB
of memory, against 22.1 GiB for H2O2RAM and 27.7 GiB for
SONIC.
For values of 128 bytes or more, we switch to a hybrid that
stores the values in a tree-based ORAM and their positions in
the hierarchical ORAM. With 1 KiB values, the hybrid serves
5.4× as many requests as the hierarchical ORAM alone and
reduces memory by 44%.
We target a failure probability below 2−64 over 232 accesses,
and we prove in Lean that a model of our hierarchical ORAM
meets this target, that every lookup returns the newest value,
and that its hash-table accesses hide the requested keys. Unlike
H2O2RAM, we also hide repeated lookups of an absent key.
1. Introduction
Trusted execution environments (TEEs) allow a cloud
service to process sensitive data while protecting those data
from the host operating system. Memory encryption alone,
however, does not hide which locations an enclave accesses.
Page faults, processor caches, and other side channels can
expose secret-dependent memory-access patterns even when
the values stored at those locations remain encrypted [1], [2],
[3]. Oblivious RAM (ORAM) [4], [5] addresses this leakage
by making the observable memory trace independent of the
logical addresses requested. We assume that the adversary
observes the address of every memory access inside the en-
clave, including accesses served by the processor caches, and
the running time of every instruction. The adversary cannot
observe the contents of registers. This model is known as
double obliviousness in prior work [6], [7], [8].
While a standard ORAM only serves reads and writes
to the dense addresses 0, . . . , N −1, we also support sparse
keys drawn from a much larger domain. Prior work calls this
abstraction an oblivious map (OMAP) [8]: it supports key–
value lookups and updates while hiding access patterns. Gol-
dreich and Ostrovsky’s hierarchical ORAM [5], [9] provides
a direct way to support these operations: it stores records in
levels, hash tables of increasing size that index application
keys. An access probes the tables from smallest to largest
and writes the requested record back to the smallest one.
The smaller tables therefore fill and must periodically be
rebuilt into larger ones. H2O2RAM [10], a recent practical
instantiation of hierarchical ORAM, demonstrates that this
approach can achieve low amortized access cost inside a TEE.
Low amortized cost, however, does not ensure low latency
for each request. H2O2RAM stops serving requests while it
rebuilds its hash tables, and its largest table can hold every
record in the ORAM. A rebuild of that table delays every
request that arrives in the meantime, even when the average
cost per access is small. To avoid these pauses, Ostrovsky and
Shoup [11] proposed a deamortization scheme that rebuilds
the tables gradually while requests continue. The old tables
must then remain queryable until their replacements are built,
so both occupy memory at once. This creates a practical
tradeoff between pauses and memory in prior deamortization
schedules [11], [12], [13].
Tree-based ORAM [14], [15], [16] offers an alternative.

requests, yet needs less memory than H2O2RAM. For larger
values, MICRORAMA stores the values in Path ORAM and
keeps their tree positions in this hierarchical ORAM.

2. Accelerating Hierarchical ORAM with Vector
Instructions
2.1. Background
Hierarchical ORAM. Our construction follows Goldreich
and Ostrovsky’s hierarchical ORAM [5], [9]. Its smallest level
is a dense array, the online stash, which every access scans
in full. Larger levels have exponentially increasing capacities
and store records in bucket hash tables. A secret hash function
assigns each key to one bucket of a table.
An access searches the levels from smallest to largest,
scanning the requested key’s bucket in each larger level. Once
a level returns the record, every later level receives a dummy
probe of a random bucket, and the access writes the possibly
updated record into the online stash. For a key found in a
table, later accesses find this newer copy first, so that table
receives no further real lookup for the key between rebuilds,
hiding whether the key is accessed again [5], [10].
Records written to the online stash eventually fill it,
so scheduled rebuilds merge records into larger levels. The
schedule depends only on the number of accesses, and each
level is rebuilt with a frequency inversely proportional to
its capacity. A rebuild must place each record in the bucket
selected by the destination table’s hash function without re-
vealing that bucket. Goldreich and Ostrovsky’s construction
and H2O2RAM [10] perform this placement with oblivious
sorting. Sorting by bucket alone does not give every bucket the
same size, so the rebuild also pads each bucket with dummy
records before the sort and removes the surplus dummies
afterward. H2O2RAM’s implementation performs both the
sort and the removal with bitonic sorts [17], [25].
Butterfly networks and merge-split. We instead rebuild the
table by routing each record to its hash bucket through a
butterfly network. Because a lookup scans only that bucket,
the network’s output is the table itself, and no sort needs to
follow it.
A butterfly network routes records into m = 2h buckets
that each hold up to Z records.1 Each record carries a secret
routing tag, and the low h bits of the tag name its destination
bucket. To build a hash table, the tag is the new table’s
secret hash of the record’s key. Each bucket starts about
half full, and dummies fill its remaining slots. The network’s
basic operation, merge-split, reads two buckets and writes the
records whose tag bit for the current stage is zero to the first
output bucket and the others to the second. A merge-split
overflows if more than Z records go to one output.
The network visits the same bucket pairs regardless of the
tags. Stage b pairs bucket i with bucket i + 2b whenever bit b
of i is zero, and splits the pair by tag bit b. After stage b,
the low b + 1 bits of each record’s bucket index therefore
match its tag. After h stages, every record is in its destination
bucket. The sequence of bucket pairs depends only on m, so
the memory trace reveals nothing as long as each merge-split
is itself oblivious.
Butterfly networks underlie several oblivious sorting algo-
rithms [18], [19], [33], but their concrete speedup over bitonic
sort remains limited, especially for small entries. One reason
is the bucket size. The probability that a bucket overflows
decreases exponentially in Z, so at a fixed load, a negligible
failure probability requires large buckets. Prior butterfly-based
sorts use buckets of at least Z = 512 records [18], [33]. A
merge-split cannot write a record directly to its output slot,
because the location of the write would reveal the record’s
tag. It instead passes the records of its input buckets through
a compaction or sorting network of depth at least log Z. These
merge-splits therefore make many passes over the data to
resolve each tag bit. A hash-table rebuild that used them would
inherit the same cost.
AVX-512 instructions. AVX-512 is an extension of the x86
instruction set, supported by current Intel and AMD server
processors, whose instructions operate on 512-bit vector reg-
isters. One instruction applies the same operation to every part
of a register, for example adding eight pairs of 64-bit integers
at once. Prior ORAMs for TEEs have used AVX-512 to speed
up the conditional copies and swaps of records [8], [25], [32]:
one instruction moves up to 64 bytes of a record, against 8
bytes for a scalar instruction.

2.2. Byte-sliced Merge-split
Routing inside registers. Our main observation is that AVX-
512 can do more than move records as a whole. If we split
each record into bytes, one 512-bit register can hold the same
byte of 64 records. One permutation instruction, given an
index vector, then rearranges this byte of all the records at
once. Applying the same indices to each byte position rear-
ranges the whole records. We therefore use buckets of 64 slots
for our butterfly network. A merge-split then loads its two
input buckets from fixed locations, rearranges their records
in registers, and stores the two outputs at fixed locations. The
secret routing affects only the permutation indices, which stay
in registers, so the merge-split accesses the same memory
locations regardless of where its records go.
Byte-sliced layout. If each record were stored contiguously,
a merge-split would have to collect the same byte from 64
records, one load per record, before each permutation. We
instead store the buckets themselves byte-sliced (Figure 1):
the same byte position of all 64 slots is contiguous, so one
vector load fetches that byte for every slot. The hash tables
stay in this layout, so a merge-split loads its registers and
stores its outputs without converting any record. With w bytes
per slot, a bucket has w byte lines, each one 512-bit vector,
and a separate 64-bit occupancy mask. The mask identifies
real records, and the remaining slots are dummies. Each slot
contains a key, value, metadata that can mark the key absent,
and routing tag. A whole record occupies one column across
the byte lines. A lookup checks all 64 slots of a bucket at once
by comparing each key byte line with a register filled with
the corresponding byte of the requested key. It then extracts
the value with one byte permutation per value line, indexed
by the matching slot.
For a merge-split of buckets X and Y , we compute two
index vectors, π0 and π1, from the current routing-tag bit and
the occupancy masks. For each byte position, we load one byte
line from each input bucket. The two-source byte permutation
VPERMT2B selects each of its 64 output bytes from the 128
bytes in these two input registers [34]. Applying π0 produces
one output bucket’s byte line, and applying π1 produces the
other’s. The same two index vectors serve all w byte lines, so
each tag moves with its record. These permutations replace the
compaction or sorting network of depth at least log Z within
a conventional merge-split.
We size the tables for 32 records per bucket in expectation,
retaining the nominal half load used in prior butterfly-network
constructions [18]. Small buckets overflow frequently, so
we give each stage a fixed-capacity residual stash for the
records that do not fit, adapting NanoGRAM’s overflow col-
lection [21]. Section 2.4 describes these stashes and their
overflow bounds.

2.3. Deamortization-friendly Hierarchical ORAM
We now build a hierarchical ORAM whose rebuilds route
records with byte-sliced merge-splits. Moreover, we design it
to make deamortization easier, namely, to let rebuilds run in
the background while requests continue (Section 3).
Read-only hash tables. An access that finds a key in a table
writes the possibly updated record to the online stash, so the
table still holds an older copy of the key. Some schemes mark
this older copy as erased, so that the next rebuild discards
it [10], [23], [26], [27], [30], [39]. Others leave the copy in
place [5], [11], [12], [24], where the newer copy shadows it:
later accesses find the newer copy first and send only dummy
probes to the older copy’s table.
Marking complicates background rebuilding. A rebuild
reads its input tables while accesses continue, so every mark
made during the rebuild would have to be logged and replayed
on the rebuilt table. We therefore leave older copies in place,
so accesses write only to the online stash, and a hash table
never changes after it is built. A rebuild then reads a fixed
snapshot of its inputs, and accesses and rebuilds never write
to the same memory.
Leaving older copies in place also makes writes cheap.
Because the newer copy shadows the older one, a write or
an erasure need not locate the older copy, so MICRORAMA
appends the new record to the online stash without probing the
hash tables, which makes these requests faster than lookups.
For an erasure, the appended record is a tombstone, whose
metadata marks the key absent. Skipping the probes, however,
reveals that a request is a write. An application that must hide
whether a request reads, writes, or erases can therefore issue
every request through one access, which probes the tables,
returns the key’s current value, and then appends the record
that the request asks for. [Tianyao: Report the latency of a
write without probes against a lookup once the library exposes
it.]
Shadowing also hides repeated lookups of an absent key.
Such a lookup finds no record to write back. H2O2RAM then
appends an unkeyed dummy record, so a repeated lookup of
the key probes the same buckets again and reveals the repe-
tition [25]. Following earlier work [23], [24], MICRORAMA
instead appends a tombstone, exactly as an erasure does. A
later access for the key then finds the tombstone first, so the
tables already probed for the key receive only dummy probes.
The top level eventually discards tombstones (Appendix A).
Incremental merges. When the online stash fills, its records
may move up several levels at once. H2O2RAM and
MegaBlocks rebuild all of these levels in one step, building a
single table from the stash and the tables of the levels [10],
[22]. We instead view this rebuild as a cascade of merges of
two tables at a time: the stash with the smallest hash table, the
result with the next table, and so on. We call each completed
table that a level passes to the next level a carry. Unlike a
rebuild in one step, a cascade produces a usable table after
every merge. Skipping ahead, Section 3 uses this to run the
merges in the background: accesses continue on the tables
built so far, so they do not stall while a large table is rebuilt.
Every merge of a cascade routes records by the hash of
the cascade’s final table, so the merges together form one
butterfly network over the final table’s buckets (Figure 3).
Comparing to a one-step rebuild, our incremental merges
essentially perform the same work, only in a different order.
The earlier merges have already routed the carry, so a merge’s
preparation routes only its level’s table, the older table, and
the merge’s last stage then combines the two tables.

remove such duplicates by sorting [5]. Our merges avoid this
sort: because a record’s routing tag is a hash of its key, both
copies reach the same merge-split in the last stage of their

2.4. Resolving Remaining Bottlenecks
Byte-sliced merge-splits leave a rebuild with little compu-
tation, so three other problems now limit hierarchical ORAM.
First, lookups become slow relative to rebuilds. A rebuild
processes whole tables in bulk. Each merge-split takes a few
register permutations per byte position, and the merge-splits
of one stage can run in parallel. A lookup instead probes one
bucket in each table, and whether each probe is real or dummy
depends on the results of the earlier probes. Vector units and
additional cores do little to shorten this chain of dependent
memory accesses, so every table on the lookup path adds to
the latency of every access. Second, memory traffic now limits
the speed of a rebuild, because each stage of the network reads
and writes every bucket of the table but does little work on
each byte. Third, the 64-slot buckets that make merge-splits
fast overflow routinely, so a rebuild must handle the records
that do not fit.
Fewer lookup probes with a larger branching factor. To
balance the rebuild and lookup costs, we deliberately give re-
builds more work so that each lookup probes fewer tables. We
increase the branching factor B, the capacity ratio between
successive levels, so that one level spans the capacity range of
log B binary levels. MegaBlocks [22] makes the same trade
in external memory, where rebuilds are cheap for a different
reason: a rebuild processes many records with good locality,
whereas each lookup makes random transfers from backing
storage. In MICRORAMA, rebuilds are cheap because merge-
splits need little computation, so the trade is worthwhile even
when all tables reside in memory.
A larger branching factor also reduces storage overhead,
because the levels below the largest one together have about
1/(B −1) of its capacity: as much as the largest level when
B = 2, but one seventh of it when B = 8.
With B > 2, a level receives B carries before it passes a
table up. As in MegaBlocks [22], each level keeps one table,
so a lookup still probes one table per level. A level adopts
its first carry as its partial table and merges each later carry
into it. Every carry into level ℓoccupies Uℓbuckets, so a
partial table of j carries has jUℓbuckets, which need not be
a power of two (Appendix B). The merge of the B-th carry
ends the level’s cycle and produces an outgoing table of BUℓ
buckets, which leaves the level as one carry into the next level.
We number the hashed levels 1, . . . , L from the smallest, the
bottom, to the largest, the top. The top never passes a table up.
It instead merges every carry with its table into a replacement
of the same T = BUL buckets, which hold N = 32T live
keys at the nominal load of Section 2.2.
Cache and register locality. The butterfly network has a
locality that prior work exploits [19], [33]: the merge-splits of
k consecutive stages combine buckets only within groups of
2k. Routing each group through these stages while it remains
in cache reduces passes through memory by about k times.
We use a cache-oblivious recursive order [19], [40], which
needs no cache-size parameter and exploits this locality at
each cache level.
The 64-slot buckets chosen for register permutations also
improve this reuse. At the same record size, a cache holds
eight times as many 64-slot buckets as 512-slot buckets, so a
group covers three more routing stages before its data must
leave the cache.
Registers give the same benefit at the smallest scale.
We fuse two consecutive stages over four buckets, so each
bucket’s current byte line stays in a register through both
stages. This halves the loads and stores of bucket byte
lines while preserving each stage’s routing permutations. We
measure the combined benefit of fusion and cache-oblivious
traversal in the online full version.
Overflow and residual records.
At the nominal load, the
number of records routed to one 64-slot bucket is approxi-
mately Poisson with mean 32, which exceeds 64 with proba-
bility about 2−22. A rebuild of a table of 220 buckets writes
every bucket at each of its 20 stages, so about four buckets
overflow on average.
We cap each bucket of the network at its 64 slots and
send the records that do not fit, which we call residuals,
to a stash shared by many merge-splits. We adapt this idea
6

===PAGE 7===
from NanoGRAM [21], which caps the buckets of its ORAM
and collects all overflow in one shared pile. The overflows of
independent buckets rarely occur together, so a shared stash
needs little capacity. One merge-split alone needs a stash
of 32 slots to keep the probability that the stash overflows
below 2−64, whereas 220 merge-splits can share a stash of 62
slots. The loads of consecutive stages, however, are positively
correlated, and a tight bound on their total overflow remains
an open problem. NanoGRAM, whose pile collects overflow
from all levels, sizes the pile by empirical simulation. We
instead give each stage its own stash and combine the stages
with a union bound (Appendix A).
The union bound is loose, but lookups never scan the stage
stashes, which would add 20 stashes to every lookup in a table
of 220 buckets. Most residuals overflowed at an intermediate
stage, although their destination bucket has room, so a final
sweep over the output table gives them a second chance (Fig-
ure 4). Writing a residual directly into its destination would
reveal that bucket. The merge instead obliviously partitions
the residuals by destination into one range bucket for each
range of consecutive output buckets, and the sweep reads the
range bucket at every output bucket in its range, whether or
not any residual belongs there. The few records that still do
not fit form the new table’s residual tier, which a lookup
scans in full whenever it probes the table. As a result, the tier
is as small as any placement of the table’s keys into 64-slot
buckets can make it, and we show one or two buckets suffice
for each tier in our default configuration (Appendix A). The
tier is offered to the sweep again at the table’s next merge,
where a different hash is used.
Duplicate keys and the stash bound. The stash bound of
each stage requires the routed records to have distinct keys.
Because our hash tables are read-only, however, an access
leaves the older copy of its key in place, so the two tables of
a merge can hold copies of the same key. At first glance, this
seems harmless: both copies carry the same routing tag, so
they meet in the merge’s last stage, whose merge-splits keep
only the newer copy (Figure 3). The problem lies in the earlier
stages, where each table is routed through its own part of the
network and the two parts share each stage’s stash. The two
copies of a key follow corresponding routes in the two parts.
In the extreme case, repeated accesses leave the two tables
with exactly the same keys, and every overflow in one part
recurs in the other.
A merge’s preparation therefore routes the older table
through every stage, including the last, and the carry joins
only in the sweep (Figure 4). The two tables thus meet only
in the sweep, which removes duplicates as in Section 2.3.
Fixed capacities. How many records overflow must not show
in a rebuild’s memory trace. Every stash, range bucket, and
tier therefore has a public capacity that depends only on the
table size, and every merge-split visits its prescribed stash
storage even when no record overflows. With fixed capacities,
the scheme fails only if a record arrives at a stash, range
bucket, or tier that is already full. We implement a checker
that bounds this probability for a given configuration. For the
default configuration with 227 records, the probability that
some capacity is exceeded within 232 accesses is about 2−69.7,
below our target of 2−64. We also prove in Lean that a model
of MICRORAMA exceeds no capacity within these accesses
except with probability at most 2−69 (Appendix C). [Tianyao:

3. Deamortized Rebuilding
Without deamortization, an access of the hierarchical
ORAM of Section 2 waits for any rebuild it triggers, and
requests that arrive meanwhile queue behind it. We therefore
run rebuilds in the background while accesses continue, bal-
ancing latency, throughput, and storage overhead.
3.1. Background Rebuilding and Pre-routing
Background
rebuilding.
Following
Ostrovsky
and
Shoup [11], each level answers queries from published
tables while a background worker builds replacements.
The worker merges the partial table with each carry from
below (Section 2.3), reading published inputs and writing to
separate storage. Publishing an outgoing table passes it to
the next level as a carry.
With enough cores, each level can rebuild on its own
core. When there are fewer cores than levels, the workers
of consecutive levels share a thread. The thread runs their
merges in short pieces, in earliest-deadline-first order, so that
a long merge at a large level does not block the rebuild of
a small level. [Tianyao: Report the longest request stall with

Background rebuilding adds no rebuild work, but costs
extra lookup probes and storage. Until a merge publishes its
output, every lookup must search its carry as a separate table,
and the merge’s inputs and output occupy memory at the same
time. To reduce the extra probes, we want each merge to
publish its output soon after its carry arrives.
Pre-routing. To publish sooner, a merge starts its preparation
early. Preparation does not read the carry (Section 2.4), and
the public rebuild schedule determines which hash the output
uses (Appendix B), so the merge starts preparation as soon as
the partial table is published, before its carry arrives. With this
pre-routing, only residual partitioning and the sweep remain
when the carry arrives. The top uses the same procedure.
Pre-routing also keeps the required rebuild speed close
to the average. In an idealized model where preparation
dominates the cost of a merge (Appendix B), each non-top
level at B = 8 must rebuild at 4.5× the access rate, only
about 3% faster than its average rate of 4.375×. [Tianyao:

3.3. Foreground Accesses
With rebuilds in the background, the access itself becomes
the bottleneck. It is a chain of dependent memory loads
(Section 2.4), because which bucket to load next is known
only after the current bucket’s keys have been compared.
To keep other computation off this chain, a single thread
computes the hashes of all its probes before the chain starts
and extracts each table’s value while the next bucket is being
fetched.
Additional threads help most when an application submits
independent requests in batches. We divide each batch among
several threads, and each thread processes up to 64 requests
together, one table at a time. Batching speeds up lookups even
on a single thread, because the bucket loads of all requests
that a thread processes together are in flight at the same time.
On Intel TDX with 48-byte values, a batch of 64 requests on
one thread raises the throughput by 1.20× with 220 records
and by 1.31× with 225 records.
A batch can contain the same key twice, and probing the
same buckets twice for one key would reveal the repetition.
We therefore find repeated keys with AVX-512 comparisons
across the whole batch, and only the first occurrence of each
key probes for real. Each later occurrence issues dummy
probes and takes its result from the occurrence before it, so
the requests of a batch take effect in batch order. Snoopy’s
load balancer deduplicates its batches in a similar way [41],
whereas SONIC requires the application to prevent concurrent
requests for the same block [32].
3.4. Correctness and Security
Background merges must keep both access guarantees of
Section 2: a lookup returns the newest value of its key, and
a key never receives two real probes under the same hash, so
the probes do not reveal whether a key is accessed again.
Freshness order. Without background merges, smaller levels
hold newer records, so searching the levels in order finds the
newest copy first. While merges run, however, a level can
hold several queryable tables, so we order the tables by when
their records were written. Each table holds the records of a
contiguous range of accesses, and a lookup searches the tables
from the newest range to the oldest. A merge combines two
tables with adjacent ranges, and its output takes the place of its
inputs in this order. The merge also uses this order to decide
which of two copies of a key is newer, so lookups always
return the newest value.
Thread safety. Each access searches a snapshot of published
tables, its probe plan. A merge atomically replaces its inputs
with its output in later probe plans, so an access sees either all
inputs or the complete replacement. Input regions are reused
only after earlier readers finish. If workers fall behind and a
level exhausts its free regions, foreground accesses wait for a
merge to complete and earlier readers to release its inputs.
Security. The adversary now also sees when each merge runs
and publishes its output, but this rebuild schedule depends
only on when requests arrive, not on their content or the stored
data.
For foreground accesses, one notable difference caused by
deamortization is that a single hash serves several queryable
tables in turn. The merges of a cascade share one hash
(Section 2.3), and a carry stays queryable until its merge
atomically replaces it with an output of the same hash. A
key nonetheless receives at most one real probe under this
hash. After the real probe, the access writes the key’s record
or a tombstone to the online stash, so later lookups find it first
and send only dummy probes to every table with the hash.
The rest of the security analysis largely follows from prior
work [5], [10] and the discussion in Section 2. In Appendix C,
we describe how we machine-check in Lean the capacity

4. Tree-based ORAM for Large Entries
For large entries, MICRORAMA stores the values of the
entries in a Path ORAM [14] and uses our hierarchical OMAP
as its position map. Path ORAM keeps each value as a block,
either in a tree [43] whose nodes are buckets of Z slots or in a
small stash. The position map assigns each block a uniformly
random leaf, and a block outside the stash always lies on the
path from the root to its leaf. An access reads the whole path
of the requested block, gives the block a fresh random leaf,
and writes the path back. Because a block’s leaf is redrawn
at every access, the paths that accesses read are independent
of the requested keys. For an absent key, the access instead
reads the path of a random leaf. The write-back, called the
eviction, fills the buckets of the path from the leaf upward, so
that each block moves as deep as its own path allows. Blocks
that fit nowhere stay in the stash, and the construction fails if
the stash overflows.
4.1. Eviction by Register Permutation
Permuting the working set. Inside a TEE, the eviction must
hide where each block goes, so the locations it reads and
writes must not depend on any block’s destination. An eviction
rearranges its working set, the slots of the stash and the path,
by a permutation that the blocks’ secret leaves determine. As
in our merge-split (Section 2.2), a permutation inside vector
registers can depend on these leaves without revealing them.
VPERMT2B selects each of its 64 output bytes from the 128
bytes of two registers, so we limit the working set to 128
slots: a stash of 64 slots and a path of at most 64 slots. In
a byte-sliced layout, the same byte of all 128 slots then fills
two registers, and two VPERMT2B instructions, one producing
the stash and one producing the path, move that byte of every
block to its destination. Evicting w-byte blocks thus takes 2w
instructions, whichever permutation the leaves select.
The stash is stored byte-sliced, and a few permutations
transpose loaded paths into byte lines and back.
Computing the permutation. We reserve stash slot 0 for the
requested block, which the access reads and updates there. The
permutation depends only on block identifiers and leaves, so
we apply Path ORAM’s greedy rule to this metadata in reg-
isters. From the leaf upward, a 128-bit mask marks unplaced
slots whose paths pass through each bucket, and branchless bit
operations select up to Z of them. Any remaining blocks go
to the 63 unreserved stash slots. The resulting index vectors
and masks form the eviction’s plan. The layout and selection
details are in the online full version. Every eviction loads and
stores the whole working set at addresses that depend only on
the public leaf, and its placement decisions stay in registers,
under the timing assumption of Section 2.2. [Tianyao: Check
BLSI and BZHI against Intel’s DOIT list, and add any that it
omits to the timing measurement of Section 2.2.]
Comparison with prior evictions. Most of our saving over
prior TEE evictions comes from moving the payload. Oblix
moves each block into place with a linear scan of oblivious
swaps over the path [7], so it passes over the payload once
per block. EnigMap moves blocks with three bitonic sorts over
the path and the stash [8], each making at least 28 passes of
compare-exchanges over the blocks. Our permutations pass
over the payload once, at two instructions per byte position.
On the same tree and working set, one eviction of 1 KiB
blocks takes 2.5 µs with our permutations, 98 µs with linear
scans, and 140 µs with EnigMap’s eviction (Section 5.3).
Computing the plan is also faster. Oblix computes the
same greedy placement, but it scans the path once for each
block, whereas our masks process all 128 slots together at a
few instructions per bucket. A bitonic sort is slower even when
it moves only metadata: on our development machine, sorting
the 128 slots by the deepest bucket each block may occupy
takes 55 ns, about twice the 28 ns of the placement loop that
it would replace. [Tianyao: Remeasure both on the evaluation
machine with four-slot buckets and branching factor four,
whose paths are about half as long as the 19-bucket path
measured.]
Two evictions per access. Path ORAM evicts only the path
that it reads, so a block in the stash descends only as far as
that path shares the block’s own path, usually just the top
levels. While the tree is first filled, no block is read again,
so on the tree of Section 4.3 the top levels saturate and the
stash grows to hundreds of blocks, far beyond our 63 slots.
After each access, we therefore evict a second path, chosen in
reverse-lexicographic order [44], which covers every bucket
on a fixed public schedule.

4.2. Parallel Eviction
An eviction’s payload work grows with block width, but
every byte uses the same plan. We therefore split each block’s
payload into contiguous ranges, one per worker. Each worker
keeps its range in a separate tree and stash, so workers write
disjoint memory. The main thread owns the metadata, looks
up the position map, and computes the plans. Workers receive
only leaves and plans. Applying the same plan to every
byte range preserves the single-threaded placement, and each
worker’s memory accesses depend only on the public leaves.
The public worker count defaults to one per 128 payload
bytes, up to four.
An access need not wait for its second eviction. The
permutation that evicts the access path also moves the re-
quested block into stash slot 0, so a worker’s part of the
payload is complete once it has evicted its byte range of the
access path. The access then returns, and the deterministic
eviction overlaps the next request and its position-map lookup
(Figure 6). This schedule removes the deterministic eviction
from an access’s latency. Sustained throughput still depends
on both evictions and is bounded by the slower of the main
thread and the workers. Section 5.3 measures the gain from
payload workers.
4.3. Bucket Size and Branching Factor
Every working-set permutation costs the same as long as
the path fits in 64 slots, so we choose the bucket size and
branching factor for locality. Following the higher-degree trees
of Gentry et al. [44], we use four-slot buckets and branching
factor four, supporting up to 232 blocks. For 218 blocks, a
path has 9 four-slot buckets instead of 17 two-slot buckets
in a binary tree, reducing random accesses. Larger buckets
also support more workers without shortening their sequential
reads (the online full version). The cost is storage: to keep the
stash tail short, we use 0.375 blocks per slot instead of the
binary tree’s 0.5, requiring 1.33 times as many slots. [Tianyao:
Report the measured speedup over the binary tree with two-
slot buckets, on one thread and with four workers.]
4.4. Failure Probability
A stash overflow is fatal because the position map has
already changed when the eviction fails. We therefore target a
failure probability below 2−64 over 232 accesses. Path ORAM
proves an exponentially decreasing stash tail only for five-slot
buckets in a binary tree that evicts only the access path [14].
No proof covers our tree, so we measure its stash tail.
We simulate up to 7 × 1011 accesses each for 220 and 221
blocks under uniformly random and sequential (round-robin)
reads. The worst case is sequential reads of 221 blocks. A
straight line fitted to its measured tail predicts that 49 stash
slots meet a failure probability of 2−96 per access, or 2−64
over 232 accesses by a union bound. The measured tail falls
more slowly at its deepest points; if it keeps falling at their
rate, 54 to 56 slots are needed, and the 63-slot stash still
overflows with probability below 2−108 per access. These esti-
mates extrapolate tails observed to about 2−32. The simulation
methods and tail curves appear in the online full version.

5.1. Methodology
Machines. We run every experiment on two cloud virtual
machines with 16 physical cores each:
• Intel TDX: a Google Cloud c4-standard-32 virtual ma-
chine with an Intel Xeon 6985P-C (Granite Rapids) proces-
sor, a 504 MiB last-level cache, and 117 GiB of memory,
running as an Intel TDX trust domain.
• AMD SEV-SNP: an Oracle Cloud VM.Standard.E6.Flex
virtual machine with an AMD EPYC 9J45 (Zen 5) proces-
sor, whose cores form two core complexes of eight, each
with a 32 MiB last-level cache, and 128 GB of memory,
running as an AMD SEV-SNP guest. Unlike the Intel
machine, it supports VP2INTERSECT. We check the attes-
tation report of every run on it against AMD’s key server.
On both machines, we use one hyperthread per core. One
core runs the benchmark harness, so MICRORAMA uses the
other 15; each baseline may use up to all 16. We additionally
launch two otherwise identical virtual machines without TDX
and SEV-SNP to measure the TEE overhead (Section 5.4). All
code is compiled at -O3 -march=native, with GCC 15.2
except for SONIC, whose build requires Clang.
Workload and metrics. We compare the systems at three
record sizes, each matching a use case (Table 2). With 4-byte
keys and 8-byte values, the map serves as an ORAM of 8-byte
words, the standard interface for general-purpose oblivious

5.3. Hybrid with Tree-based ORAM
Hierarchical versus tree-based ORAM. For large values, the
tree construction serves requests faster than the hierarchical

ways. A hierarchical lookup loads the value bytes of all 64
slots of a bucket in every table it probes, or 64w bytes per
table for a w-byte value. A tree access reads and writes two
paths of about 40 slots each, or about 160w bytes, but it first
pays a position-map lookup in the hierarchical ORAM. Small
values make this fixed cost dominate, and large values make
the per-byte traffic dominate, where the tree moves several
times fewer bytes. With 1 KiB values, the tree therefore serves
5.4× as many requests as the hierarchical ORAM on the Intel
machine (4.7× on AMD). It also uses 44% less memory,
because it stores each value once instead of in levels that hold
several versions of every table. [Tianyao: The traffic estimates

5.4. Discussion of the Results
Cost of rebuilding. Every request writes its record into the
smallest level, so every request causes rebuild work. Our
network keeps this work small: on the Intel machine, it builds
a hash table 56 to 258× faster than H2O2RAM’s bitonic sort.
Most of the gain comes from the register permutations, which
make a merge-split 7 to 8× faster than a bitonic network over
the same slots. The cache-oblivious order with fused stages
then reduces memory traffic, which makes routing another 1.7
to 2.8× faster, and on the AMD machine, VP2INTERSECT
makes a merge 1.7× faster. Further measurements appear in
the online full version. [Tianyao: Measure the cache-oblivious
14

===PAGE 15===
order on AMD.]
Background rebuilding. A fast rebuild alone does not keep
requests from waiting. When the request thread runs every
merge itself, the access that completes a carry for the top
waits 10 s at 227 records on the Intel machine, and every
request that arrives meanwhile queues behind it. Background
workers remove this pause, and they also raise throughput,
because they rebuild on cores that would otherwise stay idle:
with three workers, MICRORAMA serves 1.98× as many
requests on the Intel machine and 1.24× as many on AMD.
Running the merges in short pieces on the request thread
instead, as a level does when it shares a thread with other
levels (Section 3.1), lowers throughput by about 16%, because
a merge cut into pieces loses the cache locality of a merge run
whole. [Tianyao: The loss from running merges in pieces is
attributed to locality without counter evidence; the extra carry
probes also contribute. Explain why the gain from background
workers is smaller on AMD.]
Pre-routing. Pre-routing, which prepares each merge before
its carry arrives (Section 3.1), raises throughput where re-
building limits it. On the AMD machine, with only writes,
which keep the workers rebuilding as fast as they can, it
raises throughput by up to 1.31× with B = 4 and 1.07×
with B = 8. It also raises the throughput of lookups by 10 to
20% when the request thread runs every merge itself, because

6. Conclusion
MICRORAMA uses vectorized bulk rebuilding to change
the tradeoff between rebuild work and online probes. Be-
cause rebuilds become cheap, a larger branching factor can
trade extra rebuild work for fewer tables on the lookup
path. Background workers run these rebuilds while requests
continue, and the larger branching factor helps here as well:
it keeps the levels below the top small, so holding old and

Appendix A.
Residual Handling Details
One stash per stage. Our concentration bound uses inde-
pendent or negatively correlated overflows, but the loads of
consecutive stages are positively correlated. Every record in
a bucket after a stage was in one of the two buckets that the
stage merged, so a crowded part of the network overflows at
several consecutive stages. An overflowing bucket also passes
a full 64 records to the next stage, which makes overflow
there more likely. We therefore give each stage its own stash
and combine the stages with a union bound, which needs
no assumption about how they depend on each other. Within
a stage, overflow still concentrates. Because capping only
removes records, the overflow of a stage is at most the total
excess over 64 of the same stage’s loads in an uncapped
network, which routes the same records by the same tags
and never removes one. When the routed records have distinct
keys, these loads are negatively correlated multinomial counts
with mean at most 32, so a Chernoff bound controls their total
excess. In our default configuration, each stage’s stash holds
one or two 64-slot buckets. Additional stash-tail plots appear
in the online full version.
One bucket per range. Because the two tables meet only in
the sweep, one 64-slot bucket per range suffices, which keeps
the sweep cheap. Every record that overflows during routing
belongs to the older table, so the number of residuals in a
range depends only on that table’s keys and tags. A record
that overflows at an early stage has used only the low bits of
its tag, so the higher bits that select its range are still uniformly
random. In our default configuration, we bound the probability
that some range overflows within 232 accesses by about 2−70.6
for the merges below the top.
Partitioning residuals by range. To collect residuals by
range, we partition them recursively by destination bits. Each
split uses the order-preserving oblivious compaction network
of Sasy et al. [49], executed in the byte-sliced layout. The
partitions form a binary tree whose leaves are the range
buckets. Each node’s public capacity is the smaller of the total
input capacity and the sum of its leaves’ capacities. Because
a node contains only records destined for those leaves, it fits
whenever they all do. Bounding the number of residuals per
range therefore suffices for every intermediate partition as
well.
The depth-first traversal reuses temporary buffers and can
pause between splits in their fixed public order (Section 3.1).
Buffer optimizations appear in the online full version.
The sweep. Each carry bucket already holds exactly the
records for the output buckets with the same low tag bits,
and the remaining bits select each record’s destination among
those buckets. The carry’s stored tags lack these remaining
bits, so the sweep recomputes them in registers by hashing
each key. It therefore reads the carry in place instead of
retagging a full temporary copy. To insert records from the
carry’s tier, the sweep scans it directly after the range bucket:
in our default configuration, the tier holds at most two buckets.
Size of the residual tier. Recovering overflowed records
makes the residual tier as small as any placement of the table’s
keys into 64-slot buckets can make it. A residual remains
after the sweep only if its destination bucket is full. That
bucket stays full, because the sweep removes a main-table
copy only when it has a newer copy of the key to insert,
and it fills every slot that it frees. When the sweep ends,
a bucket to which the new table’s hash assigns X distinct
keys therefore holds min(X, 64) of them, and the tier holds
the excess max(X −64, 0) of every bucket. Any placement
of the same keys into 64-slot buckets under the same hash,
including one computed by sorting, leaves at least this many
records outside the main table. Even so, a full top of 222
buckets needs more than 64 tier slots with probability above
2−62, so the top’s tier needs two buckets.
Tombstones at the top. A merge below the top keeps every
tombstone, because the tombstone may still hide an older
copy of its key in a larger level, or protect a hash under
which a table has already received a real probe for the key
(Section 3.4). The top consumes carries in order, and each of
its merges replaces the old top, which retires the older hashes
that a tombstone in the carry protects. The top can therefore
discard tombstones, but only after they have taken effect in its
merge: an erasure of x must still remove the old top’s copy
of x, from the main table and from the residuals, before the
merge drops the tombstone.
Some tombstones can be dropped as soon as the top reads
the carry. A tombstone is unshadowed when the lookup that
appended it missed in every table of its probe plan, including
the online stash and the residual tiers, so that no older copy of
its key exists. Finding an existing tombstone does not establish
this. The top omits unshadowed tombstones before they oc-
cupy output slots, so requests for absent keys do not consume
the nominal capacity N = 32T, which counts live keys. The
carry itself stays intact for earlier readers (Section 3.4).
The sweep drops the remaining tombstones before it tests
a bucket’s capacity. Otherwise a record could overflow into
the final residual tier although a tombstone that is dropped
later frees a slot in its bucket, and the tier would exceed the
excess max(X −64, 0) above, with X counting live keys.
For each destination bucket, the sweep therefore first drops
the older residuals that the carry replaces or erases, removes
the old top’s copies of the keys in the carry’s tier, and drops
every tombstone. Only then does it merge the carry into the
bucket, so every record that it places is the newest copy of a
live key.
Failure probability. The checker of Section 2.4 bounds each
capacity under ideal hash functions, and each bound holds for
any request sequence fixed in advance. It adds these bounds
by a union bound over the first capacity test that fails, so it
requires no independence between them.

occupies its first W slots, which can trivially be the under-
construction bank itself, so only the remaining W slots are
additional workspace. Two banks and this workspace therefore
reserve 3W per level, giving M ≥3S0 ≃12N before
metadata. The workspace is used only by the rebuild and never
holds a published table, so the two-slot lifetime constraint
used for s = 6 is unchanged. We retain a fixed workspace
at each level and assume no cross-level scratch pooling or
alternative compact-array rebuild.

Computing a shared hash. Each routing hash applies AES
under the secret key to the key together with a public pair,
the level and carry ordinal of the last carry that uses the hash.
To compute the pair, start from level ℓand carry ordinal v,
and follow the forwarding step whenever ℓis non-top and v
is a multiple of its branching factor Bℓ: replace (ℓ, v) with
(ℓ+ 1, v/Bℓ) and repeat. The terminal pair names the hash.
For uniform B = 4 and at least three levels, (1, 16) forwards
to (2, 4) and then to (3, 1). All three publications therefore
use the pair (3, 1), which each producer can compute before
its consumer runs. The same rule applies to mixed factors
because each step uses that level’s public Bℓ.
Partial tables of non-power-of-two size. A partial table with

For power-of-two Uℓ, factor j = r2e with odd r. Routing uses

unit partial occupies seven units instead of eight, saving one

Appendix C.
Machine-checked Guarantees
The correctness and security of MICRORAMA rest on
three claims. No stash, range bucket, or tier may overflow
within 232 accesses except with probability below 2−64 (Sec-
tion 2.4), no key may receive two real probes under one
routing hash, and every lookup must return the newest value
of its key (Section 3.4). Our checker bounds each capacity
on its own and assumes that the merges handle their records
as described. The other two claims have so far rested on
arguments in prose, even though one hash serves a sequence
of tables, a batch can repeat a key, and the top discards
tombstones. We therefore wrote a model of MICRORAMA
in the Lean proof assistant [50], whose kernel checks every
step of a proof, and proved all three claims for the model.
The model. The model is a reference implementation of
MICRORAMA written as Lean functions. It builds the carries
from the online stash, runs the merges below the top with
their stage stashes, range buckets, and sweeps, prepares and
merges the top, and initializes the map. Every merge checks
each capacity and reports the first one that is exceeded. The
model runs the merges one after another, as a single thread
would, and uses the parameters of our default configuration
with 227 records and of its variant with branching factor eight
at every level. Its hash functions are ideal: each routing hash
assigns every key an independent, uniformly random 64-bit
word, and each dummy probe reads a fresh random word.
The request sequence is an input fixed before the words are
drawn, so the client is non-adaptive, as in our checker.
No capacity overflows. For every request sequence fixed in
advance, the model exceeds some capacity within the first 232
accesses with probability at most 2−69, and its first overflow
falls in any later window of 232 accesses with probability at
most 2−64. Over K windows, the model therefore overflows
with probability at most 2−69 + (K −1)2−64. The proof
follows our checker: it bounds the capacities of each merge

The access pattern hides the requests. The second theorem
formalizes the security argument of Section 3.4 for the hash
tables. The adversary sees the bucket that each request, or each
request of a batch, touches in every hashed table of its probe
plan, together with the sequence of probe plans, which records
every publication. The online stash and the residual tiers add
nothing to this view, because every access scans them in full.
For every request sequence, and every schedule of probe plans
that orders its tables from newest to oldest as Section 3.4
requires, the view is within 2−69 + (K −1)2−64 of what a
simulator produces from the schedule, the batch boundaries,
and the type of each request alone. Without an overflow, the
two distributions are equal. Two request sequences that agree
on this public information thus produce views within twice
this distance.
The proof establishes that no key receives two real probes
under one hash for every request sequence, including repeated
keys within a batch, carries that keep their hash across publi-
cations, and tombstones at the top. Every real probe therefore
reads its own uniformly random word, and every dummy
probe reads a fresh one. The view is then a fixed function
of distinct entries of a uniform tape, which gives it exactly
the simulator’s distribution, and the capacity theorem bounds
the probability that MICRORAMA departs from this view.
Lookups return the newest value. For every request se-
quence and every choice of the hash words, each lookup
in the model returns the value of the newest record that the
initialization or an earlier request wrote for its key, or reports
the key absent if this record is a tombstone or does not exist.
In a batch, the earlier requests include those before the lookup
in the same batch. The proof formalizes the freshness order
of Section 3.4, including the tombstones that the top discards.
It also shows that these lookups touch exactly the buckets of
the view above, so the second theorem covers the accesses
that return these values.
Matching the model to the engine. A theorem about the
model says nothing about MICRORAMA unless the engine
computes what the model computes. For the bottom level’s
carry construction, we prove in Lean that a transcription
of the native algorithm, over 64-bit words and bit masks,
produces exactly the model’s carry. For everything else, a
replay harness runs the engine, records every table it publishes
and every bucket each access touches, and compares them
with the model evaluated in Lean on the same requests. On
64 runs covering both of our configurations, branching factors
2, 4, and 8, initialization, batches, two rebuild schedules, and
forced overflows at every kind of merge, 7,053 published
tables match slot by slot, and each forced overflow fails in the
model at the same capacity. Across these runs, the touched
buckets and the real or dummy choice match the model at
every one of more than 5.3 million table probes, both when
merges run in pieces between accesses and when every merge
runs whole before the next access. This evidence covers the
runs we executed, not every request sequence.
