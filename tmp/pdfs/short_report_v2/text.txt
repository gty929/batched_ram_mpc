COLLEAGUE BRIEFING / 14 OCTOBER 2026
Cost of a private database
Seven-page briefing: ten-party malicious MPC and two-party semi-honest computation.
Prioritize batched interactive designs. For garbled RAM, derive independent state copies from
sequential service time before pricing the fleet. Neither design yet has a measured deployment
budget.
The service we are evaluating
The target is 10,000 key-value reads per second, with mean response time below five seconds, for 228 or 232
records. Keys and values are each 32 bytes; parties are in the same AWS availability zone. Pages 2-4 retain the
ten-party model, tolerating four malicious parties with abort. Pages 5-6 assess a separate two-party,
semi-honest setting.

New two-party result: the evaluator changes the comparison
A few hundred independent garbled states are not a defensible default for this workload. At 100 ms per
complete lookup, 70% utilization requires 1,429 states; at 500 ms it requires 7,143. Under the modeled
two-epoch retention policy, those cases cost $0.99B/$13.56B and $4.31B/$65.84B per year for the two
database sizes, before complete CPU and renewal costs.
Streamed Circuit OPRAM avoids retaining future garbled programs and can parallelize a batch within one state.
Its explicit Boolean template costs $70.44M/$89.08M per year for network and SSD resources at batch 256 and
one state. That state count requires batch service within 17.92 ms, which has not been demonstrated. Joint
fresh-position generation is a small traffic term; private routing remains expensive.
These are conditional research estimates with different security guarantees and resource coverage, not comparable production
quotes or universal lower bounds.

02 / TEN-PARTY INTERACTIVE DESIGN
What the interactive estimate includes
The working design places two cuckoo hash tables over binary Circuit OPRAM, a batched oblivious-memory
construction. Every lookup probes both tables in parallel, checks the full key, and returns a value and
membership result. Oblivious access hides the requested locations; even logical reads update the private
placement state.
A central dispatcher forms batches before assigning them to independent replicas. Within each replica, several
machines per party divide the state and computation. Each replica carries a complete, independently evolving
ORAM state. This replication is a major reason the fleet is much larger than the raw database suggests.

Map packing is the number of labels per recursive record; the interactive ORAM tree remains binary.
Why batching alone does not solve the cost
Batching exposes parallelism, but private comparisons, metadata conversion, payload movement,
recursive-map updates and eviction still require substantial work. A private dot product can communicate one
reduced output while performing many local multiplications. Counting only communicated outputs therefore
misses a major cost driver.
At 10,000 reads/s, forming a 128-query batch adds only about 6.35 milliseconds of mean waiting. The
several-second response time comes mainly from computation and dependent exchanges. Moving work
offline may reduce response latency, but its steady-state production must still be paid for.
The larger model has a lower selected latency because memory requirements force a larger parallel allocation. This is not evidence
that increasing the database size improves performance. Both configurations are grid-search selections, not proven global optima.

Which assumptions move the answer most?
CPU and scheduling. For 228 records, independently optimized faster- and slower-CPU scenarios cost $1.52
billion and $6.06 billion/year. Disabling resource overlap gives $3.96 billion/year. These are scenario results,
not confidence limits.
Placement. The headline estimates assume same-availability-zone placement without marginal inter-party
transfer fees. Cross-zone traffic is charged at $0.02 per transmitted GB across both endpoints in the retained
price snapshot. Network placement can overwhelm compute savings.
Central assumptions include 2 billion weighted field operations/s per 64 vCPUs, 0.2 ms per exchange, 65% NIC efficiency and 70%
operating utilization. None is a measured guarantee for this MPC service.

04 / TEN-PARTY GARBLED-RAM MODEL
Preprocessing and retention dominate
Garbled RAM prepares an encoded computation before queries are evaluated. Few online rounds do not imply
low total operating cost: at 10,000 reads/s, the prepared computation must be replenished continuously. In
this model, about 97.7% of transmitted bytes are preprocessing.
The estimate assumes networking is the throughput bottleneck and sets garbled-stack and associated adaptor
costs to zero under a proposed migration of a two-party optimization. This is a conditional multiparty
construction, not an executed ten-party benchmark. CPU evaluation and a five-second response time have not
been established.
The prepared horizon is a major budget choice
An epoch is the number of future queries prepared in advance; it is not a batch that waits to fill. Longer epochs
amortize setup-related work over more queries but retain more garbled tables. The reference keeps two
complete epochs, representing the current and next execution, plus encoded state.

What must be solved before this becomes a service estimate
The ledger does not fully price malicious correlation generation, joint hidden-state initialization, secure
epoch renewal, or the necessary representation conversions. Accepting a continuing stream of external client
queries also needs a service-security argument beyond the cited standalone protocol.
Securely carrying a live state into the next epoch requires more than re-encoding its bits. The model also leaves
local evaluation speed, SSD throughput, machine allocation and cloud capacity unvalidated. The
sequential-throughput issue on page 5 also prevents treating these resource figures as a validated
10,000-read/s fleet. Two-party coefficients cannot be substituted directly into this malicious model.

05 / TWO-PARTY SEMI-HONEST: GARBLED MERGE
Sequential evaluation drives replication
Both two-party models use two cuckoo tables of 2N slots, two probes and an eight-entry stash; each stored
payload has 513 bits. Accounting uses 128-bit labels, FreeXOR and 32 bytes per AND (half gates), with 16-byte
merge joins counted separately. This is a backend substitution, not the artifact's native ThreeHalves gate size.
What PicoGRAM establishes [1, 2]
PicoGRAM describes its evaluator as mostly sequential. Its online-optimized variant already avoids DDH/SIMD
garbling: a 64-bit RAM access takes 9.73 ms at 216 words; 25 ms at 224 and 41 ms at 230 are paper
extrapolations. These are not timings of garbled merge or of a two-probe, 64-byte lookup. Removing DDH
therefore does not establish a faster evaluator; merge adds PRF work.
Recursive maps must return old positions before outer paths can be fetched; reinsertion and eviction modify
shared state. The two cuckoo tables can run on two lanes, but adding cores does not give linear speedup for
successive accesses to either table. SIMD and inter-request overlap need an implemented schedule.
Required copies S = ceil(10,000 x L / 0.70), where L is the complete state service time in seconds,
including maintenance before the next query. 128 copies require L <= 8.96 ms; 500 require L <= 35
ms.

sensitivity with unimplemented reset/handoff and assumed visit statistics, not a measured latency or circuit-depth bound.

06 / TWO-PARTY SEMI-HONEST: STREAMED BATCHES
Trade retained programs for interaction
The evaluator reveals retired ORAM fetch positions (or independent dummy paths) to the garbler, which
supplies and streams the next circuit. This removes the hidden-runtime stack/merge machinery and
future-program retention. Circuit OPRAM exposes parallel work within a batch, potentially reducing the
number of complete state copies [3].
Joint positions are a small incremental cost
Generate fresh leaf bits as the XOR of the parties' private contributions inside the circuit. FreeXOR adds no
AND gates; input labels and OT still cost traffic. Keep live replacement positions hidden; resolve duplicates
secretly and substitute dummy fetches. At batch 256, the conservative fresh-position allowance is only
17.92/23.04 KB per lookup. Joint hidden initialization remains separate work.

Batch latency must justify the state count
S = ceil(10,000 x Lbatch / (0.70 x B)). One state at B = 256 requires service <= 17.92 ms. At B = 1,024 the
allowance is 71.68 ms: a 50 ms batch needs one state; a 500 ms batch needs seven. Mean batch-fill waiting is
another 51.15 ms at B = 1,024. CPU throughput alone does not establish these latencies.
Larger batches expose more concurrency but increase this template's sorting work: at B = 1,024, table traffic is
541.2/665.7 MB per lookup and the one-state resource estimate is $91.68M/$114.62M per year. Replication,
measured CPU and renewal must be added consistently.
Storage benefit: stream and discard consumed tables, while retaining live ORAM state and bounded working buffers. The table uses
16 bytes per state bit at each party. Compact XOR shares can shrink that representation, but require secure input conversion/OT on
touched state; that saving is not included.

07 / RECOMMENDED NEXT STEPS AND SOURCES
Measure service time before choosing a fleet
Continue the ten-party interactive study and prototype the two-party streamed design separately. The
two-party opportunity is parallelism within a shared batch state and less retained garbled code; its current
gate template is substantially larger per query than sequential GRAM.
1. Measure a complete state cycle
For garbled merge, measure both table probes, recursive maps, PRFs, label/table I/O, eviction and the
proposed reset/renewal mechanism. Report state service time and active core-seconds separately. For batch
OPRAM, measure full batch depth, dependent exchanges and worker scaling, including duplicate queries,
misses and map-block conflicts.
2. Optimize, then enforce the throughput constraint
Specialize metadata, pool cleanup and private routing; tune packing and the flat base together. Derive copies
from measured service time at 70% utilization, then optimize horizons, workers and storage. Include
preprocessing replenishment and queueing tails. A few hundred sequential states, or one batch state, must be
justified by that measurement.
3. Calibrate cost and security together
Validate joint hidden initialization, position refresh, state transitions and lifetime overflow bounds. Reprice
measured CPU, network and storage I/O on the intended topology. Streaming does not remove live state;
neither short-epoch renewal nor compact state conversion is free. The original ten-party goal still requires
malicious security with abort.
Price basis. Two-party figures use AWS US East Linux/shared On-Demand prices refreshed 14 October 2026 (feed version
20261012193925): c6in.32xlarge $7.2576/hour, 200 Gbps NIC; gp3 $0.96/GiB-year. Network planning uses 65% efficiency, 70%
distributed efficiency and 70% utilization, with both roles charged. These factors are not measured protocol throughput.
Scope. Flat read-only key-value service with private client-supplied hash indices; no Merkle proofs. Setup, a client gateway, backups,
failover reserve, support, taxes and engineering are unpriced. Coverage differs across tables; every quoted range is conditional, not
a confidence interval or complete budget.
